# AI 协作记录

> 本文件记录本次测评中 AI 实际参与的部分、我如何核验它的输出，以及哪些地方**改掉**了它的结论。
> 不提交完整对话，只保留能说明判断过程的关键片段与证据。

## 2. 关键交互片段

### 片段 1 · 需求抽取：PDF 文本层坏了，改用页面图读取

- **上下文与完成标准**：把任务书 1.2 / 2.1 / 2.2 / 4.1 抽成"功能点 + 计算口径 + 验收用例"三张清单，数字必须与 PDF 完全一致。
- **AI 产出**：先用文本提取，得到的是一串乱码（`������Ƹ / ȫջ����`）——PDF 内嵌字体的字符映射异常。
- **核验**：没有拿乱码硬猜，而是让 AI 把 4 页渲染成图片后逐页读取；再把表格里的数字（100,000.00 / 20,000.00 / 40,000.00 / 6 只标的）与 `投资组合示例数据.json` 交叉核对。
- **采用/修改**：采用图片读取结果，并在 `VERIFY.md` 中把这 4 页要点固化为断言。**教训**：AI 对"读不到"的东西会倾向于编，必须要求它换一种可验证的取证方式。

### 片段 2 · 数值方案：整数分 + BigInt 交叉相乘

- **上下文与完成标准**：任务书 2.1 要求"阈值比较使用展示舍入前的数值"，AC-02 要求 30.00% 与 50.00% **恰好等于**阈值时两项提醒都解除。
- **AI 产出**：设计阶段 AI 先给的是常见写法——用 `Number` 算 `市值 / 总资产`，再与 `0.3` 比较，展示时 `toFixed(2)`。
- **核验**：我没有接受这个方案，要求先用断言把边界钉住再写实现，三组用例必须同时成立：
  `compareToThreshold(3_000_000, 10_000_000, 3000)` = 0（恰好等于）、`3_000_001` = 1、`2_999_999` = -1；
  另加 `pct2Of(2,3) === 6667`（66.67% 而不是 66.66%）验证四舍五入。浮点在"恰好等于"这一侧无法稳定通过。
- **采用/修改**：改为"金额=整数分、占比=百分比×100 的整数、阈值=万分比"，比较用 `BigInt(市值)×10000 > BigInt(总资产)×阈值bps`，
  展示时才做一次整数四舍五入。这一条直接决定了 AC-02 能否稳定通过，也是我认为本项目最重要的一个技术判断。

### 片段 3 · AC-04 场景摆错顺序：脚本"通过"了，但结论是错的

- **上下文与完成标准**：AC-04 要求"**分别从原组合**测试买入 A01 数量 201"，后端应拒绝且不改变有效结果。
- **AI 产出**：截图脚本在已经模拟了两笔操作（卖 A01 100、买 A02 100）之后，再提交"买入 A01 201"。
- **核验**：断言"应出现 INSUFFICIENT_CASH"失败——因为卖完之后现金已经是 25,000，201×100=20,100 **确实买得起**。
  也就是说：不是后端错了，是**测试场景的前置状态错了**。回看任务书原文"分别从原组合测试"才发现问题。
- **采用/修改**：脚本改为"先清空操作序列 → 确认现金回到 20,000.00 → 再提交 201 股"，并补充两条断言：
  操作序列仍为 0 笔、提醒数仍为 2 项。此后截图 03 才真正对应 AC-04。
- **教训**：验收用例的"前置状态"本身就是规格的一部分；AI 很容易把"能跑通"当成"符合要求"。

### 片段 4 · 前端 `hidden` 被 CSS 覆盖：截图一眼看出来的 bug

- **上下文与完成标准**：横幅（只读提示、数据校验）默认隐藏，仅在查看方案/数据异常时出现。
- **AI 产出**：用 `hidden` 属性控制显隐，同时给 `.banner` 写了 `display: flex`。
- **核验**：第一次真实截图里，初始页面顶部赫然出现"只读查看 · 正在查看已保存方案"和红色"数据校验"横幅——因为作者样式 `display` 覆盖了 `hidden` 的默认 `display:none`。
- **采用/修改**：加全局 `[hidden]{display:none !important}`，并顺手修掉"原始组合模式下每条提醒还多显示一句原占比"的冗余。
- **教训**：`hidden` 不是"银弹"，组件一旦设置 `display` 就必须显式处理；这类问题单测抓不到，**真实渲染截图是必要证据**。

### 片段 5 · 测试运行器在受限环境里 spawn 失败

- **上下文与完成标准**：`npm test` 要能一条命令跑完 37 条断言。
- **AI 产出**：`node --test`（默认按文件派生子进程）。
- **核验**：在本机沙箱里报 `spawn EPERM`——环境禁止子进程。这不是测试代码的问题，但会让"验证记录"无法复现。
- **采用/修改**：保留标准 `npm test`（普通环境可用），额外提供 `npm run test:inproc`（单进程加载同一套测试文件），
  两者跑的是同一套断言，本机实测 37/37 通过。**教训**：验收命令要能在目标环境里跑通，否则等于没有验证。

## 3. AI 输出核验清单（本项目实际执行过的检查）

| 检查 | 方法 | 发现过的问题 |
| --- | --- | --- |
| 计算是否正确 | 先写 AC 断言，再跑实现；边界用"恰好等于"用例 | 浮点比较不可靠（片段 2） |
| 接口是否按契约返回 | `curl` 打印真实响应体，逐字段核对 | PowerShell 读错误流为空，改用 curl 才看到真实错误体（服务端其实是对的） |
| 服务能否启动 | 启动后先打 `/api/health`、`/api/portfolio` | `url is not defined`（handler 上下文漏传），启动即 500 |
| 页面是否正确 | 无头浏览器全页截图，人工核对数字、层级、状态 | `hidden` 被 CSS 覆盖（片段 4） |
| 流程是否闭环 | CDP 脚本驱动真实点击，跑完 5 个场景并断言页面数字 | AC-04 前置状态错（片段 3） |
| 数据是否真的落盘 | 打开 `data/plans.json` 看结构；重启后再读 | 方案必须冻结基准快照，否则重开会漂移（见 DESIGN D2） |
| 文档与实现是否一致 | 按任务书 4.1/4.2 逐条对照仓库文件 | 初稿漏了"空方案/失败态"的交互说明，补进 DESIGN 1.4 |

## 4. 考虑过但没有采用的方案

| 方案 | 未采用原因 |
| --- | --- |
| Express + React + Vite 的标准全栈骨架（AI 的默认脚手架建议） | 本机无网络、npm registry 不可达，装不上依赖；对"单页 5 区块 + 7 个接口"来说启动成本高于收益。改用零依赖方案后，评审者 `node server.js` 即可运行 |
| 把每次模拟的完整结果（逐标的市值/占比）存进方案 | 会形成"操作序列"和"结果快照"两份真相；口径演进后历史方案数字无法解释。改为只存操作 + 冻结基准 + 指纹，打开时复算 |
| 前端也实现一遍占比计算做交叉校验 | 两套舍入必然对不上，运行期会互相打脸；交叉校验应放在测试层（独立重算），运行期只信后端一份口径 |
| 用 `toFixed(2)` 处理占比与金额 | `toFixed` 受二进制浮点影响（如 1.005 → "1.00"），与"展示舍入前数值参与比较"的要求冲突；改为整数分与整数 pct2 |

## 5. 结论

AI 在这类任务里最大的价值是**把设计快速变成可运行的东西**，最大的风险是**用"能跑"冒充"符合要求"**。
本次真正花时间的不是写代码，而是：把口径钉死（整数运算）、把场景摆对（AC-04 从原始组合出发）、把结果看一眼（截图里的横幅、金额、比例）。
这三件事都发生在"AI 输出之后"，也是我认为测评真正想看的环节。
